### Product Suggestion: Revision Selection When Cloning

When cloning an analysis, preserve the original pinned revision by default for
reproducibility, but provide an explicit option to choose the revision for the
new run. The user should be able to:

- Keep the original commit.
- Resolve the latest commit from the originally selected branch or tag.
- Select a different branch, tag, or exact commit.

The clone screen should display both the source analysis revision and the
revision that the new analysis will run before submission. This would support
iterative pipeline debugging without forcing users to recreate parameters and
analysis settings manually, while retaining a safe reproducible default.

### Product Suggestion: Direct Pipelines and Tools Navigation

Provide a direct, persistent navigation route to **Pipelines and Tools** from
Advanced Analytics. Currently, the discoverable route starts on the analyses
page and requires clicking **Run Analysis**, even when the user's intent is to
browse, import, inspect, or manage tools rather than immediately run one.

A dedicated navigation item or clearly labelled link would make tool management
easier to discover and would separate the concepts of managing workflows from
launching an analysis.

### Product Suggestion: Sort Workspace Project Data

In the **Add Data** modal, under **Workspace Project Data**, make the
**Created At** column sortable. Sorting newest-first would make recent pipeline
outputs substantially easier to locate when a project contains many analyses
and similarly named result directories.

### Product Suggestion: Collision-Safe Result Mounting

When mounting analysis results into an interactive session from an analysis
**Results** page, the mount fails if a folder with the same name already exists
in that session. For example, two pipeline runs may each publish a folder named
`results`; after mounting one, the second cannot be mounted under the same
name.

Provide a mount-name field or automatically generate a unique destination name
from stable run context, such as the analysis name plus a short job identifier
or timestamp. The UI should show the proposed destination before mounting and
allow the user to change it.

Also allow users to select and mount the complete results folder directly from
the analysis **Results** page. John could not find a way to select the whole
folder there, although whole-folder selection works through **Add Data** using
the **Workspace Project Data** modal. Aligning these two paths would remove the
need for a workaround and make repeated-run comparison easier.

## Two-Process File-Flow Experiment

After preserving the successful hello-world state on `john_test_01`, branch
`john_test_02` was created for a distributed file-handoff experiment. The new
entry point is `file_flow.nf`.

- `PRODUCE_FILE` creates `message.txt` containing `Hello from producer`.
- Nextflow passes `message.txt` to `CONSUME_FILE` through a `path` channel.
- `CONSUME_FILE` verifies the expected input text and creates `final.txt` with a
  second line, `Processed by consumer`.
- Both processes use the confirmed image
  `ghcr.io/pgscatalog/pyyaml:6.0`.
- Each process records its hostname, working directory, and relevant SHA-256
  checksums in a context file.
- Producer outputs publish under `results/producer`; consumer outputs publish
  under `results/consumer`.

The experiment is intended to confirm separate Azure Batch task submission,
dependency ordering, Azure Blob work-directory staging, downstream input
localisation, data integrity, and final output publishing. Different container
hostnames confirm separate containers, but do not by themselves prove that the
tasks ran on different Azure VMs. Azure node or pool metadata would be needed
to establish physical worker placement.

Local validation uses the exact Lifebit Nextflow version, `22.11.1-edge`, in an
isolated Docker container. The first execution attempt required a local-only
`--max_memory 1.GB` override because the validation container had less than the
repository's default 6 GB request. It then showed that the validation image did
not provide a `hostname` executable, so the diagnostics were made more portable
by reading `/etc/hostname` instead.

After that adjustment, both `PRODUCE_FILE` and `CONSUME_FILE` completed

shell primitives were also tested directly in the amd64
`ghcr.io/pgscatalog/pyyaml:6.0` image. Local validation does not prove Azure
Batch behavior, but it confirms DSL2 parsing, dependency ordering, file-channel

Lifebit constructs the Nextflow command by injecting an Azure configuration and
a generated parameter configuration. It also enables the DAG and trace, uses
`-process.cache lenient`, passes `-resume`, runs in the background, and provides
Lifebit-specific executor, region, and deployment parameters. Storage account,
project, job, workflow-session, and deployment URL identifiers are
intentionally omitted.

The generated execution trace is available through the Lifebit UI.

The reason for `-process.cache lenient` is understood and does not require
Lifebit follow-up. Standard Nextflow caching fingerprints file inputs using
their path, size, and modification time. Lenient mode ignores modification time
and uses path and size, avoiding false cache misses when Azure or shared-storage
staging changes timestamps without changing file content. The residual risk is
limited to resumed runs where an input is replaced with different content at
the same path and exact size; immutable or versioned inputs plus recorded
checksums mitigate that risk. Keep this behavior in mind when troubleshooting
resume results.

Lifebit documentation distinguishes three data-access mechanisms relevant to
large files:

- Azure interactive-session linked data is streamed with BlobFuse, appears
  under `filesystems`, and does not consume session storage.
- **Copy items to the session instead of linking** creates a read-only copy
  under `mounted-data-readonly` and consumes the Mounted Data volume.
- Nextflow `path` inputs are localized into Azure Batch task work directories;
  the single-file ingress experiment confirmed this behavior for a small file.

The exact copy count, reuse behavior, cleanup lifecycle, worker-disk impact, and
cost model for large Azure Batch inputs remain unknown. This is now the primary
Lifebit follow-up before production-scale genomic data is introduced.

## Data Ingress Findings

The next investigation is how Lifebit's file selector propagates user-selected
data into Azure Batch tasks.

- Lifebit documentation says pipeline input parameters can be populated through
  the file-selector control.
- File Explorer organises project data into Analyses Results, Cohorts, and Data.
- Data may be uploaded from a local machine where deployment policy permits,
  linked/imported from approved cloud locations, imported from another
  analysis, or exposed through catalog data. Azure behavior may differ from the
  AWS-focused documentation and must be verified empirically.
- Interactive-session mount paths such as `/home/jovyan/...` are scoped to that
  session and must not be passed to Azure Batch as pipeline inputs. Select the
  platform file so Lifebit emits its cloud-backed path instead.
- AWS Accelerated File Staging and Mountpoint guidance does not apply to this
  confirmed Azure deployment.

The `pgsc_calc` CSV samplesheet is parsed by the Nextflow controller. For each
row, a relative `path_prefix` is resolved against the samplesheet's parent
directory. A pfile prefix expands to `.pgen`, `.pvar`, and `.psam`. Therefore,
the safest initial cloud layout is:

```text
pgsc-toy/
  samplesheet.csv
  cineca_synthetic_subset.pgen
  cineca_synthetic_subset.pvar
  cineca_synthetic_subset.psam
  PGS001229_22.txt
```

with this samplesheet row:

```text
sampleset,path_prefix,chrom,format
cineca,cineca_synthetic_subset,22,pfile
```

The file selector would provide `samplesheet.csv` as `--input` and the concrete
score file as `--scorefile`. The genotype paths should remain relative inside
the CSV so the parser resolves them within the same cloud directory. Direct
`az://` values in `path_prefix` have not been validated and the parser's current
absolute-path check only recognises paths beginning with `/`.

Before using genomic files, the proposed minimal experiment is a new branch
with one required `input_file` parameter. A single process will receive that
file through a Nextflow `path` input, record its name, size, and SHA-256 hash,
copy it to results, and allow comparison with the source. Selecting the prior
run's small `message.txt` through Workspace Project Data would test the complete
UI-to-Azure staging path without production data.

### Single-File Ingress Experiment

John approved this experiment. Branch `john_test_03` was created from the
accepted file-flow revision and uses `input_stage.nf` as its main script.

- Required custom parameter: `input_file`
- Optional parameter: `outdir`, defaulting to `results`
- The workflow validates that `input_file` was supplied.
- `Channel.fromPath` resolves the selected platform path and checks that it
  exists.
- `STAGE_INPUT` receives the file through a Nextflow `path` input, causing
  Nextflow and Azure Batch to stage it into the task work directory.
- The process copies the staged file to `received.txt` and records the staged
  name, byte size, SHA-256 checksum, container hostname, and working directory.
- Results publish under `results/input`.

The intended source is the synthetic `message.txt` generated by the successful
`john_test_02` analysis, selected through Lifebit's file dialog. No production
or participant data is required.
