## Fully Qualified Docker Hub Batch Test

After committing the inventory and registry evidence on `john_test_03`, branch
`john_test_04` was created for an isolated Azure Batch test.

- Main script: `hello.nf`
- Container: `docker.io/library/ubuntu:22.04`
- Output: `results/hello.txt`
- Expected content: `Hello from Lifebit`
- No schema or profile is required.
- Custom run parameter: `outdir=results`.

This differs from the failed Batch test only in using a fully qualified Docker
Hub image reference. Success would identify unqualified image handling as the
likely original failure. Failure would point to Batch-specific image validation
or networking rather than interactive-session registry access.

Local validation passed. The amd64 Docker Hub image pulled and executed the
expected shell command, and `hello.nf` completed under Nextflow `22.11.1-edge`
with the local executor and a local-only 1 GB memory cap. Azure Batch remains
the acceptance test.

The fresh Lifebit analysis at revision
`bff3ba6a280844a39b372199786ed36580758a68` completed successfully on Azure
Batch. This confirms that `docker.io/library/ubuntu:22.04` is valid in both the
interactive and Batch execution planes. The original invalid-image failure was
caused by the unqualified `ubuntu:22.04` reference in this Nextflow/Azure Batch
path. Fully qualify all container image references for this deployment.

An independent uncached `podman pull alpine:3.20` succeeded in 2.348 seconds.
Podman explicitly reported that `alpine` was resolved through
`/etc/containers/registries.conf.d/shortnames.conf` to
`docker.io/library/alpine:3.20`. Interactive short-name success therefore
depends on Podman's alias configuration and does not apply to Azure Batch.

Inspection of upstream Nextflow tag `v22.11.1-edge` at commit
`4fc071ff773fee7c0d3d3b52e6ab92f9e4e362dd` confirmed the executor mechanism.
`AzBatchTaskHandler` passes the process task to `AzBatchService`; `createTask()`
reads `task.getContainer()` and passes that exact string to Azure Batch through
`TaskContainerSettings.withImageName(container)`. The upstream unit test
explicitly verifies that `ubuntu:latest` remains unchanged. The configured
default registry server `docker.io` is used for pool registry credentials, not
for qualifying process image names. The inspected `nf-azure` source contains no
Podman, `shortnames.conf`, or `registries.conf` handling.

The precise conclusion is that interactive Podman applied a local alias while
Nextflow passed the unqualified image reference unchanged to Azure Batch, which
rejected it in the observed run. There is no evidence that the Batch worker
literally lacked `shortnames.conf`, and the post-mortem should not make that
claim.
